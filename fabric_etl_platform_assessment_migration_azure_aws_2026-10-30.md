# Microsoft Fabric ETL Platform Assessment and Migration Strategy

**Evidence-based comparison: Microsoft Fabric vs. Azure-native ETL vs. AWS-native ETL**  
**As of:** 30 October 2026  
**Planning baseline:** Existing Fabric **F4 / 4-CU** capacity; Azure Blob/ADLS Gen2 and containerized ETL are treated as examples of the current state, **not verified inventory**.  
**Decision:** Which ETL/ELT pipelines should move to Fabric, which should remain on separately operated Azure services, and under what conditions would AWS-native services be preferable?

> **Evidence convention.** References such as [S1](https://learn.microsoft.com/en-us/fabric/data-factory/connector-overview) point directly to vendor documentation at the end. “Supported” means the named product supports a capability, not that every connector/mode/authentication/network combination works. Recommendations and priority levels are **analyst assessments**; no internal logs, actual job manifests, network topology, measured capacity utilization, or compliance approvals were provided. All proposed pilot thresholds are decision criteria, not measured facts.

## Executive summary

**Recommendation: adopt Fabric selectively as the analytical ETL/ELT destination, not as a forced replacement for all Azure containers or Azure Data Factory pipelines.** It is a strong candidate for recurring Blob/ADLS ingestion, relational incremental loads, tabular transformations, Delta Lakehouse curation, and downstream Power BI datasets. A containerized job that relies on arbitrary Python packages, custom authentication, custom network access, non-tabular outputs, or side effects should stay on container infrastructure unless a pilot proves an equivalent implementation is both operable and more economical. Fabric's product-level coverage is broad but the connector, trigger, security and upgrade details are **not uniformly interchangeable with ADF**. [S1](https://learn.microsoft.com/en-us/fabric/data-factory/connector-overview) [S2](https://learn.microsoft.com/en-us/fabric/data-factory/compare-fabric-data-factory-and-azure-data-factory/) [S3](https://learn.microsoft.com/en-us/fabric/data-factory/data-factory-limitations) [S41](https://learn.microsoft.com/en-us/azure/data-factory/how-to-upgrade-your-azure-data-factory-pipelines-to-fabric-data-factory) [S43](https://learn.microsoft.com/en-us/fabric/data-factory/upgrade-best-practices)

**AWS is an excellent native ETL choice when source data and operating expertise are already in AWS.** Glue + S3 + Step Functions/EventBridge + CloudWatch + Lake Formation provides a complete AWS-family stack. Moving Azure-resident data and operational workflows to AWS solely for ETL introduces cross-cloud networking, identity, egress, and governance considerations; no quantified benefit has been established for doing so. [S11](https://docs.aws.amazon.com/glue/latest/dg/connectors-chapter.html) [S27](https://docs.aws.amazon.com/eventbridge/latest/userguide/using-eventbridge-scheduler.html) [S28](https://docs.aws.amazon.com/glue/latest/dg/monitoring-awsglue-with-cloudwatch-metrics.html) [S35](https://docs.aws.amazon.com/glue/latest/dg/glue-data-quality.html) [S36](https://docs.aws.amazon.com/lake-formation/latest/dg/what-is-lake-formation.html)

**F4 is a capacity constraint, not a dedicated 8-vCPU machine for every Fabric service.** Its documented base allocation for *capacity-billed Spark* is **8 Spark vCores**, and the F4 Spark queue limit is **four**. Spark, pipelines, SQL, and BI compete for the capacity budget, with smoothing, bursting, and throttling rules. OneLake storage, optional on-demand billed Spark, and eligible user licenses may be separate costs. Use the Fabric Capacity Metrics app in the pilot. [S18](https://learn.microsoft.com/en-us/fabric/data-engineering/spark-job-concurrency-and-queueing) [S19](https://learn.microsoft.com/en-us/fabric/enterprise/optimize-capacity) [S20](https://learn.microsoft.com/en-us/fabric/data-engineering/autoscale-billing-for-spark-overview) [S21](https://learn.microsoft.com/en-us/fabric/enterprise/throttling) [S23](https://learn.microsoft.com/en-us/fabric/enterprise/metrics-app-timepoint-page) [S49](https://learn.microsoft.com/en-us/fabric/enterprise/licenses)

**Three gating issues require proof before migration:** (1) exact connector × operation × gateway × authentication support; (2) compliance with private-network, identity, data-residency and audit policies; and (3) throughput and p95 end-to-end completion time at F4 under *concurrent* BI/reporting load. Microsoft's ADF upgrade workflow can assess and upgrade eligible pipelines, but complex triggers, some long-tail connectors, dynamic authentication, and advanced network configurations remain gaps or require redesign. [S3](https://learn.microsoft.com/en-us/fabric/data-factory/data-factory-limitations) [S38](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview) [S41](https://learn.microsoft.com/en-us/azure/data-factory/how-to-upgrade-your-azure-data-factory-pipelines-to-fabric-data-factory) [S42](https://learn.microsoft.com/en-us/fabric/data-factory/migrate-planning-azure-data-factory)

## 1. Scope, architecture and current-state assumptions

### 1.1 The three native platform families

| Layer | Fabric-native | Azure-native, without Fabric | AWS-native, without Azure or Power BI |
|---|---|---|---|
| Ingestion | Fabric Data Factory Copy activity / Copy job | Azure Data Factory (ADF) Copy; Azure Functions or container extraction where necessary | AWS Glue jobs/crawlers or Lambda for lightweight extraction |
| Raw storage | OneLake Lakehouse Files / shortcut to existing source | Azure Blob Storage / ADLS Gen2 | Amazon S3 |
| Batch transformation | Dataflow Gen2 / Spark notebook / Fabric Warehouse SQL | ADF Mapping Data Flow / Azure Container Apps Jobs / Synapse Spark or SQL | AWS Glue Spark / Lambda / EMR as needed |
| Streaming | Eventstream → Eventhouse; Spark streaming for special workloads | Event Hubs → Stream Analytics / Azure Data Explorer / custom containers | Kinesis/MSK → Glue Streaming / Managed Service for Apache Flink |
| Orchestration | Fabric pipelines, schedules, event-based patterns | ADF schedules/triggers; container-job schedulers; Azure Monitor | Step Functions, EventBridge Scheduler, Glue workflows |
| Quality and governance | Pipeline/SQL/Spark tests + Fabric lineage + **separately metered Purview DQ** as needed | Container/ADF validation + Microsoft Purview | Glue Data Quality + Glue Catalog + Lake Formation |
| Observability | Monitoring hub, workspace monitoring, Fabric Capacity Metrics | ADF Monitor, Azure Monitor/Log Analytics | CloudWatch logs/metrics, Step Functions history |
| Analytics | Lakehouse SQL endpoint / Warehouse → Power BI | Synapse serverless/dedicated SQL → traditional Power BI | Athena/Redshift → Amazon QuickSight/Quick |

### 1.2 What “Azure Containers” means in this assessment

**Terminology caveat:** “Azure Containers” can also mean **containers inside an Azure Blob Storage account**—a storage namespace, not a compute service. If that is the intended meaning, the relevant current-state stack is **Blob containers + an actual ETL runtime** (for example ADF, Functions, VM or a separate app), and the Container Apps findings below are optional. The runtime must be identified during discovery.

The specific current compute tool was not identified. For workloads that really are containerized code, this assessment uses **Azure Container Apps Jobs** as a representative baseline because jobs run finite tasks on demand, on schedules, or from events and suit Python-based ETL. An existing Azure Container Instances (ACI), AKS, Functions container, Kubernetes CronJob, or Azure Batch deployment has different runtime/network/scale/operational characteristics and must be mapped separately during discovery. Container Apps supports VNet integration, scaling, secrets and Azure Log Analytics, but **the image and Python logic remain application code that your team owns**. [S16](https://learn.microsoft.com/en-us/azure/container-apps/jobs) [S17](https://learn.microsoft.com/en-us/azure/container-apps/overview) [S26](https://learn.microsoft.com/en-us/azure/container-apps/log-monitoring)

**Current state to verify before making a go/no-go decision:**

1. Inventory every Azure container/job, ADF pipeline, dataflow, SSIS package, Spark job, and downstream data consumer; record its owning team and business impact.
2. For each source/target, record endpoint, region, data classification, file format, volume, frequency, maximum latency, REST/API limits, database CDC availability, identity, firewall and egress constraints.
3. Record live baseline metrics: bytes/rows read and written, wall-clock p50/p95 runtime, job cost, retry and failure rates, peak concurrency, data quality SLA and RTO/RPO if applicable.
4. For Fabric F4, export capacity consumption and throttling around the same ETL and BI time windows before judging “spare” compute. [S21](https://learn.microsoft.com/en-us/fabric/enterprise/throttling) [S23](https://learn.microsoft.com/en-us/fabric/enterprise/metrics-app-timepoint-page)

### 2.2 High-impact network/authentication caveats

- **Private Link is not transparent across Fabric experiences.** Microsoft's security documentation describes engine-specific behavior, including a documented limitation on copying data to/from a Data Warehouse with Fabric private link enabled. A secure Lakehouse copy working does **not** establish parity for Warehouse, Spark, Dataflow and BI clients. [S38](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview)
- **ADLS shortcut limitations** include cross-tenant authentication differences and restrictions around managed-private-endpoint-backed storage accounts. A shortcut also provides access to the external target; it doesn't copy/migrate the underlying data or magically eliminate the source's authorization controls. [S40](https://learn.microsoft.com/en-us/fabric/onelake/create-adls-shortcut) [S44](https://learn.microsoft.com/en-us/fabric/data-engineering/lakehouse-git-deployment-pipelines)
- **AWS Glue JDBC jobs have a subnet design constraint:** a single ETL job's JDBC connections use one subnet; multiple sources must be accessible from it. IAM, security groups, DNS, routing, VPC endpoints, Secrets Manager, and cross-account permissions remain real work. [S12](https://docs.aws.amazon.com/glue/latest/dg/connection-properties.html) [S54](https://docs.aws.amazon.com/glue/latest/dg/aws-glue-programming-etl-connect-jdbc-home.html)
- **Azure containers have the widest code flexibility**, but with that flexibility come image security, base-image patching, dependency pinning, retry logic, and application-level telemetry duties. Container Apps provides managed execution and log integration, not automatic ETL semantic correctness. [S16](https://learn.microsoft.com/en-us/azure/container-apps/jobs) [S17](https://learn.microsoft.com/en-us/azure/container-apps/overview) [S26](https://learn.microsoft.com/en-us/azure/container-apps/log-monitoring)

**Practical gate:** for each proposed migration, build an executable matrix of `[connector, source/sink operation, auth method, gateway path, private-link requirement, schema, throughput]`. A single failed *mandatory* combination blocks that migration path until a tested workaround exists.

### 3.2 F4 compute model — a necessary correction to simple vCPU comparisons

- Fabric **F4 = 4 CUs**, documented **8 base Spark vCores** for capacity-billed Spark. Its current Spark concurrency/queue documentation lists **24 max Spark vCores under the relevant burst factor** and a **queue limit of four**. Bursting is **not free sustained dedicated capacity**, and does not guarantee that concurrent workloads maintain their performance. [S18](https://learn.microsoft.com/en-us/fabric/data-engineering/spark-job-concurrency-and-queueing) [S19](https://learn.microsoft.com/en-us/fabric/enterprise/optimize-capacity)
- Fabric data pipeline, Spark, Warehouse SQL and Power BI work use a shared capacity accounting model rather than receiving an isolated eight-core cluster each. Background operations are smoothed across the documented window, and overload can cause throttling or rejection. [S19](https://learn.microsoft.com/en-us/fabric/enterprise/optimize-capacity) [S21](https://learn.microsoft.com/en-us/fabric/enterprise/throttling) [S23](https://learn.microsoft.com/en-us/fabric/enterprise/metrics-app-timepoint-page)
- Fabric's **on-demand Spark billing** is a separate option: when enabled, Spark jobs are charged separately and **no longer consume** the same shared Fabric capacity. This is useful for bursts but changes the cost comparison. [S20](https://learn.microsoft.com/en-us/fabric/data-engineering/autoscale-billing-for-spark-overview) [S57](https://learn.microsoft.com/en-us/fabric/data-engineering/billing-capacity-management-for-spark)
- ADF Mapping Data Flows run on managed Spark execution clusters priced by active vCore-hours. AWS Glue standard DPUs are a separate compute/memory unit; neither nominal vCore counts nor memory allocations establish equal throughput. [S52](https://learn.microsoft.com/en-us/azure/data-factory/concepts-data-flow-overview) [S47](https://aws.amazon.com/glue/pricing/)

**Illustrative transformation-only economics (not a benchmark):**

### 3.3 Performance and scalability: what the documents prove vs what requires testing

| Criterion | Fabric F4 | Azure ADF + containers | AWS Glue |
|---|---|---|---|
| Scale mechanism | Capacity SKU, Spark node allocation, queues/bursting; optional separately billed on-demand Spark | ADF managed Data Flow cluster sizes; containers scale replicas and vCPU/RAM as configured | Select Glue worker/DPUs; separate job runs and streaming scaling |
| Isolation | **Shared F4** unless dedicated/isolated capacity or on-demand Spark is chosen | ADF jobs and containers are separately metered; orchestration and data services still have their own limits | Glue metered jobs, shared S3/catalog, independent orchestration limits |
| Small frequent jobs | Simple orchestration; Spark cold starts and capacity overhead should be measured | Container Job and ADF startup/runtime need measurement | Glue bootstrap overhead needs measurement |
| Long heavy parallel jobs | Higher risk of F4 CU contention and queues | Scale selected jobs/containers independently, at usage cost | Scale DPUs/jobs independently, at usage cost |
| Reproducibility | Dataflow/SQL/notebook definitions plus environment/version discipline | Container image digest and IaC/Git/ADF definitions | Glue script/library version, IaC/Catalog schema |
| Proven performance winner | **Not determined from published SKU numbers** | **Not determined** | **Not determined** |

For a fair proof-of-concept, use the **same input data, transformations, quality assertions, output format/partitioning, concurrency and SLA**, then measure: (i) end-to-end p50/p95 runtime including startup; (ii) CPU/memory and shuffle; (iii) bytes copied and scanned; (iv) the cost *of the entire pipeline*; (v) throughput under 1× and 3× loads; (vi) concurrent report latency; (vii) recovery after source/API failures. Vendor infrastructure docs explain the relevant scaling mechanisms but do **not** prove application-level equality. [S18](https://learn.microsoft.com/en-us/fabric/data-engineering/spark-job-concurrency-and-queueing) [S21](https://learn.microsoft.com/en-us/fabric/enterprise/throttling) [S28](https://docs.aws.amazon.com/glue/latest/dg/monitoring-awsglue-with-cloudwatch-metrics.html) [S52](https://learn.microsoft.com/en-us/azure/data-factory/concepts-data-flow-overview)

### 3.4 Streaming is not a batch-pipeline replacement

Fabric supports Eventstream to Eventhouse and Activator, with supported sources including Event Hubs, Kafka variants, SQL CDC and selected external systems; eventstream destinations have configuration and supported-combination limits. Azure can instead operate Event Hubs, Stream Analytics/ADX, Functions or custom consumers; AWS uses Kinesis/MSK and Glue Streaming or Flink. AWS Glue Streaming documents continuous billing while running and checkpoint/recovery semantics, while specialized real-time mode has additional functional restrictions. [S13](https://learn.microsoft.com/en-us/fabric/real-time-intelligence/get-started-with-real-time-intelligence) [S14](https://learn.microsoft.com/en-us/fabric/real-time-hub/supported-sources) [S15](https://docs.aws.amazon.com/glue/latest/dg/add-job-streaming.html) [S50](https://learn.microsoft.com/en-us/fabric/real-time-intelligence/event-streams/add-manage-eventstream-destinations) [S55](https://docs.aws.amazon.com/glue/latest/dg/streaming-chapter.html)

**Migration rule:** move streams only after proving event ordering/late data handling, deduplication, watermark/replay, stateful joins/aggregations, delivery semantics, poison-message handling, retention and end-to-end latency. A stream can be “supported” but fail the business correctness contract.

### 6.2 Operational runbook and ownership (proposed)

**Data engineering owner:** ETL logic, schemas, idempotency, reconciliation, job definitions, rerun/backfill procedure. **Platform owner:** Fabric CU/capacity, workspaces, gateway or Azure/AWS runtime configuration, budgets and support ticket routing. **Security owner:** source credentials, credential rotation, tenant settings, identity grants, private link/VNet access. **Data owner:** quality thresholds, classification, retention, business signoff. **BI owner:** freshness/latency of reports and semantic models. Name primary and backup on-call contacts for failures, and define maximum response, escalation and replay windows before production cutover.

### 6.3 Compliance questions that can block migration

- Is Fabric approved for the specific regulated dataset and region, **including** transient processing, logs, gateway, external shortcut and Purview scan location?
- Must all traffic stay inside a private network? Does each selected Fabric engine support the required inbound/outbound path and identity, rather than only the Lakehouse itself? [S38](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview) [S56](https://learn.microsoft.com/en-us/fabric/security/connect-to-on-premise-sources-using-managed-private-endpoints)
- Is customer-managed key control mandatory for each layer? Are encryption, key rotation, retention, backup, deletion and legal hold controls equivalent?
- Does the current container use certificate-only authentication, embedded custom libraries, native binaries, privileged container capabilities, outbound allowlists, or private DNS assumptions that Fabric cannot reproduce?
- Can the engineering team export sufficient immutable audit records and respond to incidents without shell access to managed Spark/SQL nodes?

**No platform recommendation overrides security approval.** If any mandatory condition fails, prefer retaining the working Azure path while using a permitted read-only analytical landing or designing an approved intermediary.

## 7. Comparative assessment vs. current state: Azure containers + Blob

**Why the current Azure baseline matters:** Blob is storage, *not* ETL compute. A container provides arbitrary application logic and isolation, and ADF provides declarative copy/orchestration. Fabric Lakehouse offers native managed tabular storage and analytics but cannot automatically replace every program that writes to Blob. The fairest comparison is the **complete workflow contract**, not OneLake-vs-Blob storage capacity alone. [S16](https://learn.microsoft.com/en-us/azure/container-apps/jobs) [S17](https://learn.microsoft.com/en-us/azure/container-apps/overview) [S1](https://learn.microsoft.com/en-us/fabric/data-factory/connector-overview) [S2](https://learn.microsoft.com/en-us/fabric/data-factory/compare-fabric-data-factory-and-azure-data-factory/)

| Decision dimension | Fabric migration advantage | When current Azure containers/Blob/ADF wins | AWS family judgment |
|---|---|---|---|
| End-to-end analytics integration | OneLake, SQL, Spark and Power BI in a common managed surface | Existing raw/object workloads without Power BI/Delta need | Useful where downstream BI and workloads already reside on AWS |
| Python/external side effects | Notebooks handle supported Python/Spark ETL | Full container image, executable binaries, OS packages, custom APIs and bespoke recovery | ECS/Glue/Lambda can remain equally flexible in an AWS estate |
| Storage lifecycle and independence | Managed lakehouse tables and shortcuts | Blob/ADLS account policy, lifecycle classes, and general-purpose object storage | S3 supports independent storage governance and lifecycle |
| Provisioning/ops burden | Less direct ETL cluster maintenance | Azure containers may already be automated; no forced rewrite | Glue reduces infrastructure management, but cross-service IAM/configuration remains |
| Performance isolation | Good if F4 has spare CUs | Dedicated job sizing prevents reporting contention | Glue job DPUs can be scaled independently |
| Security/network | Simplifies some identities and Fabric-native access | Complex VNet/SHIR/legacy routes may be already certified | Best for existing AWS-networked sources |
| Source coverage | Strong for common SQL, Blob, S3, SFTP and many SaaS patterns | Custom OAuth and connector-specific ADF behaviors may be required | Glue JDBC/custom connectors, but no universal SaaS parity |
| Governance/quality | Fabric visibility plus separately licensed Purview quality capabilities | Existing Purview/SQL policies; no migration disruption | Glue DQ and Lake Formation are mature AWS options |
| Incremental expense | May be low where F4 is underutilized | Usage-based jobs cheap for sporadic ETL | Glue DPU-hour is favorable for short, on-demand jobs |
| Migration risk | New CI/CD, connection mappings, dataset transforms, report dependencies | **No migration risk** for stable jobs | Cross-cloud rebuild often adds risk with no proven benefit |

**Assessment judgment:** Fabric is strongest as a **target operating platform for standardized analytical datasets**. Azure containers remain the safer default for highly customized integration runtimes or operational side effects. AWS should be assessed as a peer architecture, not a default destination for Azure-resident data. ## 9. Migration plan, acceptance gates and rollback

| Phase | Deliverable | Must-pass exit criteria | Rollback position |
|---|---|---|---|
| **0. Discovery & baseline** | Inventory, data-flow diagram, app and compliance requirements, current cloud bill and monitoring baseline | All candidate sources/targets, owners, credentials, network paths, baseline p95, DQ contract documented | No production change |
| **1. Feasibility screening** | Connector/auth/network matrix; ADF automated assessment where relevant | Mandatory connector, mode, gateway, private link and identity confirmed; gap log signed | Retain existing orchestration |
| **2. PoC in Dev** | Fabric connection, pipeline, notebook/dataflow, Lakehouse, validation tests; baseline Azure job in parallel | Identical source snapshot; exact keys/counts and agreed numerical tolerances; reproducible rerun | Azure remains source of truth |
| **3. Scale & resiliency** | 1×/3× dataset and realistic peak concurrency, deliberate failures, alert/runbook test | Meets p95 latency, quality and cost ceilings; no unacceptable F4 throttling or BI regression | Azure execution active |
| **4. Security/governance signoff** | Purview lineage proof, roles, managed-identity and gateway configs, audit export, data residency assessment | Security/network/data-owner approvals; documented lineage gaps accepted or closed | No traffic cutover yet |
| **5. Deployment rehearsal** | Git + Fabric deployment pipeline; environment variable/connection mapping; backfill and rollback automation | Definitions deploy and execute in Test; targets populated and validated; secrets are not stored in Git | Azure triggers remain enabled |
| **6. Controlled cutover** | Single bounded workload switched to Fabric with enhanced monitoring | Data freshness and downstream reports meet SLA for an agreed observation period | Re-enable Azure schedule; reconcile replays and watermarks |
| **7. Portfolio scaling** | Reusable runbook, scored backlog and per-pipeline economics | Repeatability, observability and budget sustained | Hold complex pipelines on Azure |

**Important:** Fabric Git/deployment pipelines move **item definitions/metadata**, not underlying Lakehouse data. ADF's built-in upgrade is presently a selective, controlled process, not an obligation to move everything. ### Proposed quantifiable acceptance tests (targets to agree with stakeholders)

- **Functional parity:** all primary keys and record counts reconcile for the full pilot window; amount/metric sums match within approved numeric and timezone tolerances; inserts, updates and deletes behave as specified.
- **Recovery:** intentionally fail after ingest and before commit; rerun twice and demonstrate idempotence, checkpoint safety, quarantined invalid rows, and consistent `business_date` handling.
- **Freshness:** Fabric end-to-end p95 completion **no more than 10% slower than the current Azure baseline** unless the data owner approves a different SLA. This is a **proposed** threshold, not a claim about Fabric.
- **Capacity/BI:** no unacceptable throttling, late reports or report p95 response-time deterioration in an F4 peak-workload rehearsal; establish a CU headroom alert from actual measurements. [S18](https://learn.microsoft.com/en-us/fabric/data-engineering/spark-job-concurrency-and-queueing) [S21](https://learn.microsoft.com/en-us/fabric/enterprise/throttling) [S23](https://learn.microsoft.com/en-us/fabric/enterprise/metrics-app-timepoint-page)
- **Cost:** compare all-in charges including compute, gateways, storage and operations; approve an explicit cost ceiling rather than declaring an ETL CU invoice of $0 to mean the pipeline is free.
- **Security and operations:** designated owner successfully demonstrates access denial for unauthorized users, audit retrieval, credential rotation, alert receipt and a timed rollback.

## 11. Recommendation and decision matrix

**Choose Fabric as the primary option when all of the following are true:** the output is a governed analytical dataset consumed by Lakehouse/Warehouse/Power BI; the exact connector/auth/network path works; the job's SQL/Spark/Dataflow logic can be reproduced and validated; the workload fits F4 headroom with concurrency; and production monitoring/audit are accepted. The greatest benefit is eliminating hand-offs between separate analytics services, not claiming that Fabric has free infinite compute. [S1](https://learn.microsoft.com/en-us/fabric/data-factory/connector-overview) [S4](https://learn.microsoft.com/en-us/fabric/data-factory/dataflow-gen2-data-destinations-and-managed-settings) [S18](https://learn.microsoft.com/en-us/fabric/data-engineering/spark-job-concurrency-and-queueing) [S21](https://learn.microsoft.com/en-us/fabric/enterprise/throttling) [S22](https://learn.microsoft.com/en-us/fabric/data-factory/monitor-data-factory)

**Keep the Azure-native pipeline when any of these are true:** the current container performs specialized non-tabular/OS operations, existing private-network/authentication controls cannot be reproduced, ADF triggers/backfills/SSIS/SAP functions fail the upgrade assessment, or the current usage-based pipeline meets SLA at lower incremental cost. Maintaining Blob/ADLS as the raw-data store while curating select datasets in Fabric through shortcuts or incremental copy is a reasonable hybrid path. [S16](https://learn.microsoft.com/en-us/azure/container-apps/jobs) [S17](https://learn.microsoft.com/en-us/azure/container-apps/overview) [S40](https://learn.microsoft.com/en-us/fabric/onelake/create-adls-shortcut) [S41](https://learn.microsoft.com/en-us/azure/data-factory/how-to-upgrade-your-azure-data-factory-pipelines-to-fabric-data-factory) [S43](https://learn.microsoft.com/en-us/fabric/data-factory/upgrade-best-practices)

**Choose AWS-native primarily for AWS-local workloads:** Glue + S3 + EventBridge/Step Functions + CloudWatch + Lake Formation is competitive and supports strong native quality/governance patterns, especially where the data and operating expertise are already AWS-centric. There is insufficient evidence to recommend moving Azure-resident data to AWS simply to replace current Azure containers. [S11](https://docs.aws.amazon.com/glue/latest/dg/connectors-chapter.html) [S15](https://docs.aws.amazon.com/glue/latest/dg/add-job-streaming.html) [S27](https://docs.aws.amazon.com/eventbridge/latest/userguide/using-eventbridge-scheduler.html) [S28](https://docs.aws.amazon.com/glue/latest/dg/monitoring-awsglue-with-cloudwatch-metrics.html) [S35](https://docs.aws.amazon.com/glue/latest/dg/glue-data-quality.html) [S36](https://docs.aws.amazon.com/lake-formation/latest/dg/what-is-lake-formation.html)

**Immediate decision:** approve a scoped Fabric assessment and **two parallel-run PoCs (Blob→Lakehouse and SQL incremental)**, subject to security approval. Defer full container/ADF migration until there is actual workload-level evidence for correctness, p95 runtime, F4 throttling/headroom, operations and total cost. Do not make a fleet-wide “Fabric is cheaper” or “Fabric is faster” claim from nominal vCores, DPUs, or product lists alone.

## Appendix A — Evidence and known unknowns

**Directly evidenced by vendor documentation:** connector support matrices and limitations, native Azure and AWS service architecture options, F4 Spark allocation/queue behavior, Fabric monitoring, optional on-demand Spark, core Purview quality/lineage features and limitations, ADF upgrade limitations, OneLake definition-only Git deployment, Glue Data Quality and Lake Formation access controls. See linked sources below.

**Unknown without internal access:** actual Azure container platform, VM vCPU/RAM and image dependencies; endpoint and identity settings; data sensitivity classification and regulatory obligations; F4 CU history and user concurrency; data sizes, transformations and retry patterns; complete cloud bills or reserved rates; production recovery targets; source licensing/cross-region transfer charges; incident/support contracts; vendor-specific exceptions granted to the organization.

**Not asserted:** guaranteed 1:1 execution speed from 8 Fabric Spark vCores vs. ADF 8 vCores vs. 4 Glue DPUs; Fabric equivalents for arbitrary OCI images; free ETL for all F4 jobs; that buying a service constitutes regulatory compliance; that all ADF pipelines can be automatically migrated.
